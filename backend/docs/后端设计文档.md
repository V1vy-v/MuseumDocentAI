## 一、项目概述

### 1.1 项目背景

本项目是"基于 RAG 的博物馆导览问答机器人"，面向历史博物馆场景，让观众通过**语音或文字**向讲解机器人提问，获得有馆内资料支撑的回答。课题要求两项高阶能力：

1. **RAG 检索增强** —— 回答必须有据可依，减少模型幻觉；
2. **上下文多轮记忆** —— 支持自然的连续对话，理解「它」「这个」这类指代。

后端承担这两项能力的服务端实现，以及模型接入、语音闭环、会话持久化。

### 1.2 后端职责与完成情况

| 能力 | 状态 | 说明 |
|---|---|---|
模型接入（ASR / 文本 / TTS） | ✅ 完成 | 同平台三个模型，已实测跑通语音闭环 |
文本问答接口 | ✅ 完成 | `/api/chat` |
语音问答接口 | ✅ 完成 | `/api/voice`，录音进 → 回答 + 播报语音出 |
多轮对话记忆 | ✅ 完成 | 按 token 预算的上下文窗口，服务重启不丢 |
指代消解 | ✅ 完成（第一级） | 规则 + 话题焦点；LLM 兜底为后续改进项 |
会话持久化 | ✅ 完成 | SQLite，含会话管理接口与滚动摘要 |

前端接入会话持久化 | ⏳ 待角色 A | 后端接口已就绪 |

### 1.3 技术栈

### 2.3 两条核心调用链

**文本问答 `POST /api/chat`**

```
0. maybe_compact(session_id)      旧对话攒够就压成摘要（多数请求什么都不做）
1. get_context(session_id)        取摘要 + 最近若干轮 + 上一轮引用的资料
2. coreference.resolve(...)       指代消解：「它是什么年代的」→「越王勾践剑是什么年代的」
3. rag.retrieve(消解后的问句)      检索资料；没命中再退回原句兜一次
4. llm_client.chat_reply(...)     人设 + 摘要 + 资料 + 历史 → 生成回答
5. remember(...) × 2              写入用户消息与回答
6. record_usage(...)              记下服务端返回的真实 token 用量
```

**语音问答 `POST /api/voice`**

```
0. maybe_compact(session_id)
1. transcribe(录音)               ASR：录音 → 问题文本
2~4. 与文本问答完全相同（取上下文 → 消解 → 检索 → 生成）
5. synthesize(回答)               TTS：回答 → WAV（base64 返回）
6. remember(...) × 2 + record_usage(...)
```

> **顺序是设计要点。** 第 2 步必须在第 3 步之前：用带代词的原文去检索，切出来的全是「它是 / 是什么 / 什么年」这类虚词片，命中数到不了阈值，必然返回空资料，模型于是回答「馆内资料暂未收录」——上一轮刚讲过，观众却觉得机器人失忆了。这一问题在改造前真实存在（见 §7.3 复现记录）。

### 2.4 三条分层原则

1. **存储细节不外泄。** `store.py` 是唯一的存储边界，`memory` 只表达"记什么、取什么"。将来换存储介质只改一个文件。
2. **模型调用只有一个入口。** 所有模型调用收敛到 `llm_client` / `tts_client`，换模型或平台只改这两处。
3. **检索保持签名不变。** `rag.retrieve(question)` 的返回格式固定，消解逻辑放在**调用方**而非 `rag.py` 内部，保证角色 C 替换向量检索时两边互不影响。

## 三、接口设计

### 3.1 接口一览

共 6 个路径、7 个操作。

| 方法 | 路径 | 用途 | 依赖模型 | 前端是否必须 |
|---|---|---|---|---|
GET | `/api/health` | 健康检查 | 否 | 联调用 |
POST | `/api/chat` | 文本问答 | 是 | 已在用 |
POST | `/api/voice` | 语音问答 | 是 | 已在用 |
POST | `/api/sessions` | 新建会话 | 否 | 可选 |
GET | `/api/sessions` | 历史会话列表 | 否 | 可选 |
GET | `/api/sessions/{id}/messages` | 拉取历史 | 否 | 可选 |
DELETE | `/api/sessions/{id}` | 清除会话 | 否 | 可选 |

详细的请求/响应示例见《接口文档.md》。

### 3.2 错误契约

统一返回**平铺**的错误体：

```json
{"error": "给开发看的说明", "hint": "给用户看的提示"}
```

**这里踩过一个真实的坑。** FastAPI 的 `HTTPException(detail={...})` 会自动再包一层：

```json
{"detail": {"error": "...", "hint": "..."}}
```

而前端 `ApiClient.handleResponse` 是按 `json.has("error")` 平铺解析的，后端自己的 `schemas/chat.py::ErrorResponse` 也声明成平铺——**三方不一致，错的是后端**。后果是模型调用失败返回 502 时，前端判定为"成功但 answer 为空"，界面上出现一个空气泡，而不是「AI 服务暂时不可用，请稍后再试」——**恰恰在最需要提示的时候失效**。

修复方式：在 `main.py` 注册异常处理器把 dict 类型的 `detail` 摊平（后端改，前端零改动），并补测试锁住这个契约。

### 3.3 兼容性设计

- **`/api/chat` 与 `/api/voice` 的入参和回参自始至终未变**，前端 `ApiClient` 一行都不用改。
- **会话管理接口全部是"可选增强"。** `/api/chat`、`/api/voice` 首次写入时会自动建会话（`INSERT OR IGNORE` 兜底），所以前端照旧自己生成 UUID、完全不调它们，问答与持久化也正常工作。只有要实现「重启 APP 恢复上次对话」时才需要调。
- **`/api/sessions` 的请求体可省略**，也可以带前端自己生成的编号，两种调用方式都支持。
- **删除幂等**：会话不存在时返回 `deleted: false` 而非报错。前端本地存了过期编号时不必特殊处理。

## 四、数据设计

### 4.1 表结构

```sql
CREATE TABLE sessions (
    session_id         TEXT PRIMARY KEY,
    created_at         TEXT NOT NULL,          -- UTC ISO8601
    updated_at         TEXT NOT NULL,
    summary            TEXT NOT NULL DEFAULT '',   -- 滚动摘要
    summary_upto       INTEGER NOT NULL DEFAULT 0, -- 摘要已覆盖到 messages.id
    title              TEXT NOT NULL DEFAULT '',   -- 取首问，供列表展示
    last_prompt_tokens INTEGER NOT NULL DEFAULT 0  -- 最近一次真实用量（安全阀）
);

CREATE TABLE messages (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id  TEXT NOT NULL REFERENCES sessions(session_id) ON DELETE CASCADE,
    role        TEXT NOT NULL,                   -- user / assistant
    content     TEXT NOT NULL,                   -- 用户原话，保真存储
    resolved    TEXT NOT NULL DEFAULT '',        -- 指代消解后的问句（诊断用）
    sources     TEXT NOT NULL DEFAULT '[]',      -- 该轮引用的资料标题（JSON）
    tokens      INTEGER NOT NULL DEFAULT 0,      -- 本条占多少 token（窗口按它算）
    created_at  TEXT NOT NULL
);

CREATE INDEX idx_msg_session ON messages(session_id, id);
```

**设计要点**

- `content` 与 `resolved` **分列存储**：前者是用户原话（展示、摘要、日志一律用它），后者只服务于检索与排查。否则对话记录会失真，也无法事后评估消解准确率。
- `summary` + `summary_upto` 让摘要成为**增量可维护**的视图：每次只压缩 `id > summary_upto` 且已滑出窗口的那一段。旧信息不丢失，只是降精度。
- `sources` 存 JSON 字符串，既落库供历史回放，也是**指代消解最可靠的焦点信号**（见 §5.1）。

### 4.2 索引、事务与并发

| 措施 | 原因 |
|---|---|
`PRAGMA journal_mode=WAL` | 读写并发，读不被写阻塞 |
`PRAGMA busy_timeout=5000` | 撞锁时等待而非直接报 `database is locked` |
`PRAGMA foreign_keys=ON` | 让 `ON DELETE CASCADE` 生效（删除会话时消息级联清理） |
每请求独立连接 | FastAPI 的同步接口运行在线程池中（多请求 = 多线程），而 sqlite3 连接默认不允许跨线程复用 |
三条语句同一事务 | 会话兜底建 + 插消息 + 更新 `updated_at` 一次性提交，避免半写入 |

### 4.3 幂等迁移

升级不要求删库重建。启动时检查列是否存在，缺了就 `ALTER TABLE ADD COLUMN`：

```python
_MIGRATIONS = (
    ("sessions", "last_prompt_tokens", "INTEGER NOT NULL DEFAULT 0"),
    ("messages", "tokens", "INTEGER NOT NULL DEFAULT 0"),
)
```

**关键细节**：新增 `tokens` 列后必须**回填老数据**（`UPDATE messages SET tokens = length(content) + 4`）。否则老消息的 `tokens` 全为 0，而窗口查询的条件是"累计 token ≤ 预算"——0 永远不超预算，窗口会变成**无界**，上下文再也不截断。这一条有专门的迁移测试覆盖。

## 五、关键技术实现

### 5.1 指代消解

**问题**：观众第二句往往省略主语——「它是什么年代的？」「这个在哪个展厅？」。这种问句直接去检索是搜不到资料的。

**策略：话题焦点 + 规则替换（第一级）**

核心不是"解析代词"，而是维护**上一轮到底在聊哪件文物**：

1. **焦点来源优先级**：`sources`（上一轮回答实际引用了哪些资料）→ 历史文本匹配知识库文件名。前者是强信号，它直接记录了上一轮讲的是哪件文物。
2. **代词表**（按长度倒序替换）：
   - 单数回指：它 / 他 / 她 / 牠 —— **语音识别常把「它」写成同音字「他」「她」，不收进来语音场景的消解会整体失效**
   - 指示代词：这个 / 那个 / 这件 / 那件 / 这只 / 那只 / 这把 / 那把 / 这幅 / 那幅
   - 短语回指：刚才说的 / 上面提到的 / 这件文物 / 那个东西 …
3. **受保护词**：`其他 / 其它 / 他人 / 他乡 / 他日 / 他国` 字形含「他」但语义不是回指。直接用占位符屏蔽后再替换、替换完还原（不能简单删除，会改变句子结构），否则「其他展厅」会变成「其越王勾践剑展厅」。
4. **刻意不收「此」「该」**：它们更常出现在「因此」「应该」「不该」里，误伤概率远高于收益，而口语提问基本不会用。

**核心原则：宁可不改，不要猜错。** 猜错会把检索带去完全无关的资料，让模型一本正经地答错对象，比不消解更糟。所以以下情况一律原样返回，并在 `reason` 里说明原因：

| 情况 | reason |
|---|---|
问句里没有代词 | `no_pronoun` |
复数/集合代词（它们 / 这些 / 那些） | `plural_pronoun` |
出现比较并列信号（分别 / 各自 / 两个 / 哪个更） | `ambiguous` |
焦点候选不唯一（上一轮引了多份资料 / 一句话提到多件文物） | `ambiguous_focus` |
会话第一句就说「它」，无上文可依据 | `no_focus` |
问句里本来就点了对象 | `already_grounded` |

**双路召回兜底**：消解有猜错的可能，所以改写后检索为空时会退回原句再试一次（成本只是多一次本地关键词匹配）。

**验证效果**（真实知识库，非 mock）：

```
改造前：直接用带代词的原文检索
  问句：它是什么年代的？
  命中：（空 —— 模型会回答「馆内资料暂未收录」）

改造后：先消解，再检索
  消解：它是什么年代的？ → 越王勾践剑是什么年代的？
  依据：method=rule  antecedent=越王勾践剑  reason=rewritten
  命中：['示例_越王勾践剑']

反向保护用例：
  其他展厅怎么走？      → changed=False  reason=no_pronoun
  应该往哪走？          → changed=False  reason=no_pronoun
  它们都是什么年代的？   → changed=False  reason=plural_pronoun
  它是什么年代的？      → changed=False  reason=no_focus
```

### 5.2 上下文窗口

**为什么按 token 而不是消息条数**：一条 500 字的资料和一句「嗯」都算一条消息，按条数切窗口完全不准；token 才是真正的资源约束。

**为什么不需要分词器**：

1. 模型接口在 `usage` 里返回真实用量（`prompt_tokens` 等），安全阀直接用服务端数字；
2. 中文经验值 1 个汉字 ≈ 1 个 token（实测 13 字 → 15 `prompt_token`，多出的 2 个是 chat 模板开销），估算只用于"何时压缩"，且宁可略大（早压缩是安全方向）。

不使用 `tiktoken`：那是 OpenAI 的词表，对本项目模型本来就不准，还要额外加依赖。

**按"轮"对齐**：窗口边界未必落在问答的分界上，直接喂给模型会出现「只有回答、没有提问」的半截上下文。实现上采取**往前补**而不是**往后砍**：

- 往后砍：预算恰好装下奇数条消息时，会一次性丢掉半轮问答（极端情况丢掉一半窗口）；
- 往前补：只多带一条消息，信息不丢。

对应的不变式已写成测试：**窗口总量最多超出"一条消息"的预算**。

**兜底**：单条消息就超过整个预算时（例如观众粘贴了一大段文字），至少保证带上最后一轮问答，否则模型连上一句都看不到。

### 5.3 长对话滚动摘要

**与常见 agent 的 compact 有一个关键区别：摘要只是数据库之上的一层"视图"。**

| | 常见 compact | 本项目的滚动摘要 |
|---|---|---|
触发依据 | token / 上下文预算 | token（滑出窗口的累积量） |
原文 | 通常从上下文中被替换掉 | **一条都不删** |
更新方式 | 整段重新总结 | **增量滚动**：旧摘要 + 新一段 → 合并 |

所以它**只改变"模型看到什么"，不改变"存什么、显示什么"**——历史接口仍能完整取回全部对话，前端照旧完整展示。这也是为什么 `summary` / `summary_upto` 两个字段在设计初期就预留进了表结构。

**触发条件**：`已滑出窗口、且 id > summary_upto` 的消息 token 总和 ≥ `SUMMARY_TRIGGER_TOKENS`。

**性能约束**：多数请求什么都不做（代价只是一次带索引的 `SUM` 查询），只有跨过阈值时才多一次模型调用。语音链路已有 ASR + 生成 + TTS 三次串行调用，延迟预算很紧。

**尽力而为**：`summarize()` 失败只记录原因并跳过，绝不影响正常问答，下一轮会再触发。

**真实模型验证**（低阈值下强制触发）：

```
压缩前   窗口内 16 条，第 1 轮在窗口里，摘要为空
压缩     触发成功：covered_messages=10, pending_tokens=264
压缩后   窗口内 6 条，第 1 轮已被挤出窗口
         摘要：「观众共提出两类问题。其一询问越王勾践剑的年代，讲解员回答该剑为
                春秋晚期越国青铜剑，1965年出土于湖北江陵望山一号楚墓，现藏于
                湖北省博物馆，展出位置在二楼青铜展厅。其二……」
         原文条数：16（摘要不删原文）

只靠摘要问答（窗口里已经没有第 1 轮了）
   问：我最开始问的是哪件文物？
   答：您最开始问的是越王勾践剑，这把剑出土于湖北江陵望山一号楚墓，
       现藏于湖北省博物馆二楼青铜展厅。
```

答案里的出土地与展厅位置**只可能来自摘要**，证明压缩确实保留了关键信息。

### 5.4 防幻觉与 RAG 对接

- 检索到资料时，把资料拼进 system prompt 并明确要求「不要编造资料里没有的内容」；
- 检索为空时，指示模型走统一的兜底回复 `NO_KNOWLEDGE_REPLY`，而不是自由发挥；
- 资料标题随回答一起返回给前端展示来源。

`rag.retrieve()` 当前是**占位实现**（2~3 字滑窗关键词匹配 + 命中数阈值），仅在有示例资料时可用。接口签名与返回格式已固定，角色 C 可独立替换为向量检索。

### 5.5 会话生命周期

| 项 | 措施 |
|---|---|
自动建会话 | 任何写入前 `INSERT OR IGNORE`，前端不调建会话接口也能用 |
会话列表 | 按最近活跃倒序；`updated_at` 精度只到秒，用 `rowid` 兜底保证**顺序稳定**（否则列表每次刷新可能换位置） |
空会话隐藏 | 建了但没发过消息的会话不出现在历史列表（与通用聊天应用行为一致），可用 `include_empty=true` 查看 |
TTL 清理 | 启动时删除超过 7 天未活动的会话（消息级联删除） |
增长控制 | 一轮问答约 200 字节，靠 TTL 已足够，不另设条数上限 |

## 六、性能实测与参数取值

本章数据均为**实测**，用于确定配置取值，而非估计。

### 6.1 模型能力

| 项 | 值 |
|---|---|
上下文窗口 | **1M** |
最大输出 | 131,072 |
输入价格 | **$0.14 / 1M token** |
输出价格 | $0.28 / 1M token |

### 6.2 延迟特性

**提示词大小与耗时的关系**（同一问题，逐级放大资料）：

| 目标 token | 实际 prompt | 输出 token | 耗时(s) | cached |
|---|---|---|---|---|
200 | 162 | 48 | 8.13 | 0 |
1000 | 750 | 62 | 10.02 | 0 |
4000 | 2976 | 33 | 4.93 | 0 |
8000 | 5916 | 35 | 5.55 | 2944 |
16000 | 11796 | 31 | 3.65 | 5888 |
32000 | 23598 | 43 | 10.61 | 11776 |
32000（第二次） | 23598 | 32 | **4.79** | **23552** |

**结论**：

1. 提示词从 162 token 拉到 23598 token，**耗时没有单调变差**——延迟并非由提示词大小主导；
2. 前缀缓存生效，重复前缀基本不重复计费（第二次同一提示词 `cached` 接近全量）。

**延迟波动**（同一提示词、同样输入，重复 6 次）：

```
10.02s / 4.19s / 9.86s / 5.74s / 16.61s / 1.49s
```

**1.49 秒 ~ 16.61 秒，相差 11 倍**。这是本项目目前**最值得关注的性能问题**：对语音导览而言，观众说完话可能等 1.5 秒，也可能等 16 秒，且不可预测。已验证该波动**与提示词设计无关**，属模型平台侧。

### 6.3 成本

12000 token 的提示词约 **$0.0017 / 次**，可忽略。

### 6.4 参数取值依据

| 参数 | 值 | 依据 |
|---|---|---|
`RECENT_TOKEN_BUDGET` | 12000 | 约 160 轮原文。一次正常参观 30~60 问 ≈ 2200~4400 token，**根本不会溢出**；成本可忽略、耗时与提示词无关，所以限制窗口的不是"装不下" |
`SUMMARY_TRIGGER_TOKENS` | 1500 | 窗口溢出后尽快压缩，避免"丢了又没摘要"的空档。实测第一次压缩落在第 289 轮左右，属安全网而非日常机制 |
`SUMMARY_MAX_CHARS` | 400 | 摘要本身也占 prompt 预算 |
`PROMPT_TOKEN_ALERT` | 200000 | 1M 上下文的 20%，留足余量 |
`SESSION_TTL_DAYS` | 7 | 演示环境足够；增长主要由 TTL 控制 |

> **窗口与触发阈值是两个不同的旋钮**：窗口 = 保留多少原文；阈值 = 滑出窗口的部分攒到多少才压缩。窗口 12000 之后正常参观不会溢出，所以阈值取小并不影响正常使用——它只在超长对话里生效。文档中的示例值可用环境变量覆盖，无需改代码。

## 八、调试工具

除 FastAPI 自动生成的 `/docs` 外，另建了**调试台**（`/debug`，单文件静态页，零构建、无外部依赖）。

`/docs` 只能逐个调接口，看不到"跨轮"的东西；调试台补上：

- **指代消解结果**：每条观众提问下标注 `它` / `这个` 被改写成了什么
- **滚动摘要**：压缩出来的摘要原文
- **token 明细**：每条消息的 token 估算值 + 最近一次请求的真实 `prompt_tokens`（窗口是按这些算的）
- **左侧历史会话列表**：标题取首问、相对时间、消息条数，点击切换
- **一键跑指代消解回归**：依次发三句，验证「它」「这个」都能正确指向
- **原始报文**：最近一次请求与响应，出错时直接看到后端的 `{error, hint}`

调试台的实现细节：因 `/api/chat` 的响应中不含消解结果（它是库里的诊断字段），调试台在每轮问答后额外拉一次 `/messages`——这同时也验证了持久化接口。

## 九、已知问题与后续改进

### 9.1 已修复的重要问题（记录以备复盘）

| 问题 | 影响 | 处理 |
|---|---|---|
检索先于消解 | 「它是什么年代的」必然检索为空，模型答「馆内资料暂未收录」 | 调整调用顺序，并补回归测试 |
错误体多包一层 `detail` | 前端错误提示整体失效，失败时显示空气泡 | 后端摊平，前端零改动 |
`smoke_test.py` 的 `MIMO_API_URL` 取到空串 | 语音验证步骤必然失败 | 改为复用 `config` |
上下文窗口按条数切 | 会把一轮问答从中间切开，模型看到没有提问的回答 | 改为按 token 预算 + 按轮对齐 |
摘要阈值换算错误 | 窗口 1200 时第 17 轮开始丢内容，却到第 76 轮才压缩，中间 59 轮信息直接丢失 | 重算并放大窗口至 12000 |
`MAX_MSG_PER_SESSION` | 定义了却从未使用，让人误以为有保护 | 删除 |

### 9.2 待改进

**高优先级**

1. **TTS 失败会导致整轮回答与历史一起丢失。** 当前 `voice.py` 把 TTS 与前面各步放在同一个 `try` 里，TTS 一旦异常（或平台未返回 `audio` 字段触发 `KeyError`），整轮返回 502——不但丢失已生成的文字答案，而且 `memory.remember` 执行不到，**这一轮不入库**，下一轮追问会断片。应改为 TTS 单独容错，失败时返回文字 + 空音频。
2. **前端接入会话持久化**（角色 A）：`session_id` 存 `SharedPreferences`，启动时拉历史回填。否则本项目的会话持久化能力在 APP 中无法体现。
3. **知识库内容**（角色 C）：目前只有 1 份示例资料，是影响回答质量最大的单一因素。
4. **前端 60 秒读超时 < 语音链路潜在耗时**：语音链路为 ASR + 生成 + TTS 三段串行，每段服务端超时 60 秒，而生成段实测波动 1.49~16.61 秒，叠加后可能超过前端等待上限——表现为 APP 报网络错误但服务端实际成功。

**中优先级**

5. **流式返回**：当前需等整段回答生成完，感知延迟即为完整生成时间。改为流式后首字可提前到约 0.5~1 秒，语音场景还能第一句一出来就开始播报。代价是 `/api/chat`、`/api/voice` 的响应形式变更，需与前端协商。
6. **向量检索**（角色 C）：当前关键词匹配没有语义能力，问「青铜器怎么铸造的」永远匹配不到《越王勾践剑》。
7. **指代消解第二级**：焦点不唯一时目前直接放弃，可增加 LLM 改写兜底（代码中 `method` / `reason` 已预留接口）。
8. **分阶段耗时观测**：目前无法知道一次请求里 ASR / 检索 / 生成 / TTS 各占多久。要优化延迟，先要能量出来——建议把分段耗时落库。
9. **重试与退避**：模型调用失败直接返回 502，瞬时抖动应退避重试。

**低优先级**

10. 焦点持久化（存为会话字段，跨窗口稳定）
11. 结构化摘要（固定槽位替代自由文本，减少增量合并的误差累积）
12. 跨会话用户记忆（需先有用户标识，APP 目前无登录体系）
13. 并发模型（同步 `def` + `requests` 跑在线程池，并发上升会耗尽线程）
14. 幂等键（客户端超时重发会重复写入一轮对话）
15. `HOST = "0.0.0.0"` 为死配置（启动靠命令行 `uvicorn --host`）
16. 补充 `.gitattributes`，统一跨系统换行符行为
