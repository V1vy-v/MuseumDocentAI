# 后端接口文档

> 简要说明各接口的用法。设计思路见同目录《记忆系统与指代消解方案.md》。
>
> 两个自测入口：
> - **http://127.0.0.1:8000/docs** —— 交互式接口文档（能点着发请求、传文件）
> - **http://127.0.0.1:8000/debug** —— 调试台，能连续多轮对话并看到
>   指代消解结果、滚动摘要、token 明细（这些东西 `/docs` 里看不到，见 `backend/README.md`）

## 启动

```bash
cd backend
pip install -r requirements.txt          # 含 zvec（向量库，win 包约 11MB）
cp .env.example .env                     # 然后把下面两个密钥填进去
uvicorn app.main:app --port 8000
```

`.env` 里两个密钥分工不同，**缺哪个影响哪块**：

| 变量 | 用途 | 不填会怎样 |
|---|---|---|
| `DEEPSEEK_API_KEY` | 文本问答、摘要、语音识别 | 问答直接返回 502 |
| `ARK_API_KEY` | 文档向量化（检索用） | 服务照常起，但检索退回关键词模式，效果明显变差 |

### 向量索引会自动建，不需要手工命令

索引目录是 `backend/data/zvec_kb/`（已 gitignore，不随仓库分发），
启动时按 `knowledge_base/` 里的资料自动切块 + 向量化：

- 第一次启动：一份资料约 1.5 秒
- 之后每次启动：只重建**改过的**文件，没改动时约 0.3 秒
- 新增/删除资料：下次启动自动增量收录/清理
- 想强制重来：删掉 `backend/data/zvec_kb*` 再启动

启动日志会明确告诉你走的是哪条路：

```
[向量库] 就绪 dim=2048 文件=1 本次变更=1 新增块=1     ← 向量检索
[向量库] 未配置 ARK_API_KEY → 检索退回关键词模式       ← 降级（接口行为不变，只是效果差）
```

## 通用约定

- 所有接口前缀 `/api`，请求与响应均为 JSON（UTF-8）。
- 时间字段是 **UTC 的 ISO8601**，例如 `2026-10-11T14:00:18+00:00`。
- 服务启动时会自动创建数据库 `backend/data/chat.db`（已 gitignore），并清理超过 7 天未活动的会话。
- 会话里**什么都不会被删**。长对话的"滚动摘要"只是改变喂给模型的内容，
  历史消息始终完整保留，`GET /api/sessions/{id}/messages` 永远能拿到全部。

### 错误格式

出错时返回非 2xx，响应体**平铺**为：

```json
{
  "error": "session not found",
  "hint": "该会话不存在或已被清理"
}
```

- `error` 给开发看（保留原始异常信息），`hint` 给用户看（可直接显示在界面上）。
- 前端 `ApiClient.handleResponse` 用 `json.has("error")` 判断即可。
- 未被业务代码覆盖的错误（例如访问了不存在的路由）仍是 FastAPI 默认的
  `{"detail": "Not Found"}`。

> 实现说明：FastAPI 的 `HTTPException(detail={...})` 默认会再包一层 `detail`，
> 所以 `app/main.py` 注册了一个异常处理器把它摊平。
> 改这个格式前请先确认前端 `ApiClient` 和 `schemas/chat.py` 的 `ErrorResponse`。

## 接口一览

| 方法 | 路径 | 用途 | 依赖模型 |
|---|---|---|---|
| GET | `/api/health` | 健康检查（含向量索引状态） | 否 |
| POST | `/api/chat` | 文本问答 | 是 |
| POST | `/api/chat/stream` | 流式问答（SSE） | 是 |
| POST | `/api/voice` | 语音问答 | 是 |
| POST | `/api/tts` | 文字转语音（任意文本） | 是 |
| POST | `/api/sessions` | 新建会话 | 否 |
| GET | `/api/sessions` | 历史会话列表 | 否 |
| GET | `/api/sessions/{id}/messages` | 拉取历史 | 否 |
| DELETE | `/api/sessions/{id}` | 清除会话 | 否 |
| GET | `/api/kb/{路径}` | 资料原文（HTML，来源点开看全文） | 否 |
| GET | `/api/kb/search` | 资料检索：关键词 + 类型/地区/类别筛选 + 分页 | 否 |
| GET | `/api/kb/doc` | 资料原文（纯文本 + 元信息，APP 用） | 否 |
| GET | `/api/kb/filters` | 筛选项（省份、文物类别及各自数量） | 否 |

「依赖模型」= 需要 `backend/.env` 里配置有效的 `DEEPSEEK_API_KEY`，否则返回 502。
其中 `/api/voice` 还依赖同一个 key 做语音识别。

## GET /api/health

联调时先打这个确认服务活着，顺带确认检索走的是哪条路。

```json
{
  "status": "ok",
  "index": {
    "ready": true,
    "dim": 2048,
    "collection": "museum_kb",
    "dir": "backend/data/zvec_kb",
    "last_sync": {"files": 1, "removed": 0, "rebuilt": 0, "chunks": 0},
    "error": ""
  }
}
```

- `index.ready` = `true` 表示向量检索可用；`false` 时 `index.error` 会写明原因
  （没配 `ARK_API_KEY`、zvec 没装、索引被占用…），此时检索自动退回关键词模式。
- 前端只需要看 `status`；`index` 是给联调排查用的。

## POST /api/chat

文本问答。**入参和回参自始至终未变，前端无需改动。**

请求：

```json
{
  "question": "它是什么年代的？",
  "session_id": "任意字符串，同一会话复用同一个值"
}
```

响应：

```json
{
  "answer": "越王勾践剑是春秋晚期的文物，距今大约两千五百年左右。",
  "sources": ["越王勾践剑"]
}
```

说明：

- `session_id` **不需要预先创建**。首次写入时服务端会自动建会话，所以前端照旧自己生成 UUID 即可。
- 服务端处理顺序：取上下文 → **指代消解** → 用消解后的问句检索 → 生成回答。
  所以「它」这类代词能正确指向上一轮讲的文物；消解结果会存进库，可用下面的历史接口查看。
- `sources` 是命中的**资料标题**数组，只用来展示，同一份资料不会重复出现。
  现在是向量检索，命中与否由语义相似度决定，所以答案里引用的内容通常能在这些资料里找到。
- 检索不到资料时会走防幻觉分支，回答「馆内资料暂未收录」而不是编造。
  涉及开放时间、门票、展厅分布这类"本馆信息"的问题如果没有资料，服务端会**直接**返回固定话术，
  不会让模型自由发挥。
- 想给用户看资料全文？用 `sources` 里的标题去下面「资料原文」接口取。
  `/api/chat` 本身为了保持兼容没有加链接字段。

## POST /api/chat/stream

**流式问答（SSE）**。请求体和 `/api/chat` 完全一样，只是响应变成一条事件流。

```json
{"question": "它是什么年代的？", "session_id": "任意字符串"}
```

响应头：

```
Content-Type: text/event-stream; charset=utf-8
Transfer-Encoding: chunked
Cache-Control: no-cache
```

事件格式是标准 SSE（`event:` 行 + `data:` 行，**空行分隔事件**）：

| 事件 | 时机 | data |
|---|---|---|
`meta` | 最先 | `{"session_id": "...", "sources": ["越王勾践剑"], "sources_detail": [...], "resolved": "越王勾践剑是什么年代的？"}` |
`delta` | 多次 | `{"text": "越王"}` —— 文本增量，客户端往气泡后面追加 |
`done` | 正常结束 | `{"answer": "完整回答", "usage": {"prompt_tokens": 279, ...}}` |
`error` | 中途出错 | `{"error": "...", "hint": "AI 服务暂时不可用，请稍后再试"}` |

`sources_detail` 是 `sources` 的增强版，**只在流式接口里给**（`/api/chat` 保持原样不动）：

```json
"sources_detail": [
  {
    "title": "越王勾践剑",
    "heading": "越王勾践剑（示例资料）",
    "url": "/api/kb/%E7%A4%BA%E4%BE%8B_%E8%B6%8A%E7%8E%8B%E5%8B%BE%E8%B7%B5%E5%89%91.md",
    "score": 0.0328
  }
]
```

| 字段 | 说明 |
|---|---|
`title` | 资料标题（和 `sources` 里的一致） |
`heading` | 命中的小节，可以显示成「越王勾践剑 · 出土与年代」 |
`url` | **可直接点开的原文地址**（相对当前服务根路径），前端用 WebView/浏览器打开即可 |
`score` | 融合后的排序分，只用于展示和排序，不要拿来当阈值判断 |

> 这个数组为空表示本轮没有命中任何馆内资料（走的是防幻觉分支）。

原始报文长这样：

```
event: meta
data: {"session_id":"s1","sources":["越王勾践剑"],"sources_detail":[{"title":"越王勾践剑","heading":"…","url":"/api/kb/…","score":0.03}],"resolved":"…"}

event: delta
data: {"text":"越王"}

event: delta
data: {"text":"勾践剑"}

event: done
data: {"answer":"越王勾践剑是春秋晚期...","usage":{"prompt_tokens":279}}
```

**要点**：

1. **`meta` 先到（实测 0.02s）**，这时模型还没开始生成——界面上可以先显示来源和消解结果。
2. **`error` 是事件，不是 HTTP 状态码**。首块一旦发出，响应头就定了，后面改不了状态码，
   所以错误只能作为事件报给前端。**客户端必须处理这个事件**，不能只看 HTTP 200。
3. **`/api/chat` 一点没变**，两个接口共用同一套前置逻辑（压缩 → 取上下文 → 消解 → 检索），
   所以行为一致。
4. 客户端中途断开时，**已经生成的部分会被落库**，这一轮不会丢。

**实测收益**（2026-10，本地直连）：

```
meta 到达        0.02s
第一个 delta     3.32s    ← 观众看到第一个字的时刻
最后一个事件     7.19s
delta 分布       59 块横跨 3.14s（真流式，没有被中间层缓冲）
```

对比非流式：同样的回答必须等整段生成完才能返回。长回答（约 3000 字）实测
**首字 1.85~3.03s vs 整段 24~30s**，感知延迟降约 10 倍，总时长不变。

**命令行自测**（`-N` 很关键，否则 curl 自己会缓冲）：

```bash
curl -N -X POST http://127.0.0.1:8000/api/chat/stream \
  -H "Content-Type: application/json" \
  -d '{"question":"越王勾践剑是什么时期的文物？","session_id":"demo"}'
```

> ⚠️ **浏览器端不能用 `EventSource`**：它只支持 GET，而这里的问句要走 POST 请求体。
> 要用 `fetch()` + `response.body.getReader()` 手动解析 SSE。
> 解码时 `TextDecoder` 必须带 `{stream: true}`，否则一个汉字被切到两个数据块里会变乱码。

> ⚠️ **中间有缓冲型代理时流式会失效**：后端日志显示"0.02s 就发了首块"，
> 但客户端要等整段才收到。验证方法是对照首块发送时间与客户端首个 `delta` 的到达时间。
> 模拟器走 `10.0.2.2`、或经过 Clash 这类代理时尤其要实测确认。

## POST /api/voice

语音问答：录音进去，回答文字 + 播报语音出来。

请求：`multipart/form-data`

| 字段 | 类型 | 说明 |
|---|---|---|
| `audio` | 文件 | WAV 录音，单声道 16bit。**16kHz 和 22kHz 都实测可用**；采样率写在 WAV 头里，服务端不挑 |
| `session_id` | 文本 | 会话编号 |

响应：

```json
{
  "question": "越王勾践剑是什么年代的？",
  "answer": "越王勾践剑是春秋晚期的青铜剑……",
  "sources": ["越王勾践剑"],
  "sources_detail": [{"title": "越王勾践剑", "heading": "越王勾践剑（示例资料）",
                      "url": "/api/kb/%E7%A4%BA%E4%BE%8B_….md", "score": 0.0328}],
  "audio_base64": "UklGRi…"
}
```

说明：

- `question` 是语音识别出的文字，界面上可以显示「我听到的是…」。
- `sources_detail` 与 `/api/chat/stream` 的 `meta.sources_detail` **完全一致**，
  带原文链接，可以直接做"点开看原文"的来源气泡。老前端不认这个字段也不影响。
- `audio_base64` 是**完整 WAV 音频**（PCM 16bit / 单声道 / 24000Hz）的 base64。
  拼成 `data:audio/wav;base64,<这段>` 直接就能播。**空串表示这次没有音频**。
- 音频**头部的长度字段是修正过的真实值**，可以直接解析出正确时长。
  （平台的原始响应是流式 WAV，长度字段写 `0xFFFFFFFF`，不修的话播放器会
  把一段 12 秒的语音算成十万多秒，进度条直接失控。）
- 录音为空返回 400。
- **没听清返回 422**（`{"error": "empty transcript", "hint": "没听清，请再说一遍"}`）。
  这时前端应提示用户重说，而不是当成失败。
- 语音识别失败和语音合成失败是**分开处理**的：合成失败只会让 `audio_base64` 为空，
  回答照常返回、也照常落库。
- **耗时**：一次完整语音问答实测约 **5.4 秒**（识别 ~1s + 生成 ~2s + 合成 ~2s，串行）。
  嫌慢的话，可以让文字先上屏、音频后到——不必等同一个响应。

## POST /api/tts

**文字转语音**。给"文本问答的回答也要能朗读"用的（APP 里点喇叭、或者自动播报）。

请求：

```json
{"text": "越王勾践剑是春秋晚期的青铜剑，现藏于湖北省博物馆。"}
```

响应：

```json
{"audio_base64": "UklGRi…", "format": "wav"}
```

- `audio_base64` 是 WAV（PCM 16bit / 单声道 / 24000Hz），
  拼成 `data:audio/wav;base64,<这段>` 直接就能播。
- 实测：一句话约 **2 秒**出音频（4.96 秒语音）。
- `text` 为空返回 **400**。
- TTS 服务不可用返回 **503**（`{"error", "hint"}`），
  **注意这时文字回答本身不受影响** —— 朗读和问答是两条独立的路。
- 为什么单独开这个接口：`/api/voice` 是"录音进 → 回答+语音出"的一整条链路，
  只有用录音提问时才有音频。文本问答想让回答出声，直接调这个接口就行，
  不必把识别和生成再跑一遍。

## POST /api/sessions

新建会话。**可选接口**——不调也能正常问答，只有想让服务端发号时才需要。

请求体可以完全省略，也可以指定编号：

```json
{"session_id": "my-own-uuid"}
```

响应：

```json
{
  "session_id": "my-own-uuid",
  "created_at": "2026-10-11T14:00:18+00:00",
  "existed": false
}
```

- `existed: true` 表示该编号已存在，直接沿用（不会清空它的历史）。
- 传空串或空白等同于不传，服务端会生成一个新的。
- **新建的空会话不会出现在下面的历史列表里**，发出第一条消息后才会出现
  （和通用聊天应用的行为一致）。

## GET /api/sessions

列出历史会话，按最近活跃倒序。界面左侧那种"对话列表"就用它。

查询参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `limit` | 50 | 最多返回几条 |
| `include_empty` | `false` | 是否连"建了但没发过消息"的空会话一起返回 |

响应：

```json
{
  "count": 2,
  "sessions": [
    {
      "session_id": "s-newer",
      "title": "青铜展厅怎么走？",
      "created_at": "2026-10-12T13:29:52+00:00",
      "updated_at": "2026-10-12T13:29:52+00:00",
      "message_count": 2
    },
    {
      "session_id": "s-kept",
      "title": "越王勾践剑是什么时期的文物？",
      "created_at": "2026-10-12T13:29:35+00:00",
      "updated_at": "2026-10-12T13:29:40+00:00",
      "message_count": 4
    }
  ]
}
```

- `title` 取首问，供列表展示；空会话没有标题。
- `updated_at` 是最近一次活动时间，列表按它倒序；精度只到秒，同一秒内按创建顺序兜底，
  所以**顺序是稳定的**（不会每次刷新都换位置）。
- 只返回展示需要的字段，**不含消息正文**，列表接口不会把整个会话拖出来。

## GET /api/sessions/{id}/messages

拉取某会话的完整历史。**APP 重启后用它把对话界面回填。**

响应：

```json
{
  "session_id": "e2e-lifecycle-001",
  "title": "越王勾践剑是什么时期的文物？",
  "summary": "",
  "created_at": "2026-10-11T14:05:00+00:00",
  "updated_at": "2026-10-11T14:05:12+00:00",
  "messages": [
    {"role": "user", "content": "越王勾践剑是什么时期的文物？",
     "sources": [], "created_at": "…", "resolved": "越王勾践剑是什么时期的文物？"},
    {"role": "assistant", "content": "越王勾践剑是春秋晚期的文物……",
     "sources": ["越王勾践剑"],
     "sources_detail": [{"title": "越王勾践剑", "heading": "",
                         "url": "/api/kb/%E7%A4%BA%E4%BE%8B_….md", "score": 0.0}],
     "created_at": "…", "resolved": ""},
    {"role": "user", "content": "它是什么年代的？",
     "sources": [], "created_at": "…", "resolved": "越王勾践剑是什么年代的？"}
  ]
}
```

字段说明：

| 字段 | 说明 |
|---|---|
| `title` | 取首问，供历史列表展示 |
| `summary` | 长对话滚动摘要；对话还短时是空串 |
| `messages[].content` | **用户原话**，未经改写 |
| `messages[].resolved` | 指代消解后的问句，**诊断用**，界面展示请用 `content` |
| `messages[].sources` | 该轮回答引用的资料标题 |
| `messages[].sources_detail` | 同上，但**带原文链接**：`[{title, heading, url, score}]`，形状与流式 `meta.sources_detail` 一致，可以直接复用同一套渲染 |
| `messages[].tokens` | 这条消息占多少 token（估算值，**诊断用**：上下文窗口就是按它算的） |
| `last_prompt_tokens` | 最近一次请求的真实 `prompt_tokens`（来自服务端 `usage`，**诊断用**） |

> `sources_detail` 是**服务端按标题现算的**（库里只存标题，原文链接不落库），
> 所以**重启 APP 后回填历史，来源链接照样能点开**，老会话也自动补上。
> 区别只有一点：`heading`（命中的小节）属于当次检索的上下文，历史里找不回来，会是空串。

会话不存在（或已被 TTL 清理）返回 **404**。

## DELETE /api/sessions/{id}

清除会话及其全部消息。

```json
{"ok": true, "deleted": true}
```

- **幂等**：会话不存在时返回 `deleted: false`，不报错。前端本地存了过期编号时不必特殊处理。
- 消息随会话级联删除。

## GET /api/kb/{路径}

**资料原文**。给 `sources` 里的资料提供"点开看全文"的入口。

```
GET /api/kb/%E7%A4%BA%E4%BE%8B_%E8%B6%8A%E7%8E%8B%E5%8B%BE%E8%B7%B5%E5%89%91.md
```

- 返回一个**已排好版的 HTML 页面**（不是 JSON），直接丢给 WebView / 浏览器即可。
- 路径就是 `sources_detail[].url`，前端**不需要自己拼接**，直接用返回值。
- 只允许访问 `knowledge_base/` 目录内的文件，路径穿越（`../`）会被拒。
- 文件不存在返回 404。
- 这个接口不进 `/docs` 的接口列表（它是工具接口），但可以正常调用。

## 知识库：怎么加资料

**是的，把文件丢进 `backend/knowledge_base/` 就行**，重启一次自动收录。

```
backend/knowledge_base/
├── 越王勾践剑.md          ← 文件名 = 资料标题
├── 曾侯乙编钟.md
├── 展厅路线.md
└── 青铜器/                ← 子目录也可以
    └── 铸造工艺.md
```

规则（都实测过）：

| 项 | 说明 |
|---|---|
支持格式 | `.md` / `.txt`（其他后缀会被忽略） |
`README.md` | **会被跳过**，它是给人看的目录说明，不算知识 |
标题 | 取**文件名**（去掉扩展名）。`示例_` / `demo_` / `sample_` 前缀会被自动去掉，所以 `示例_越王勾践剑.md` 的标题是「越王勾践剑」 |
切块 | 按 Markdown 的 `#` 标题分小节，小节内按空行分段，合并到约 300 字一块。**所以标题层级写得清楚，检索就更准** |
生效时机 | **重启服务**（服务启动时做增量同步，只重建改动的文件，约 0.3 秒） |
删除资料 | 删掉文件后重启，索引里的对应内容也会消失 |
想强制重建 | 删掉 `backend/data/zvec_kb*` 再启动 |
谁负责 | 内容是角色 C 的事；新增资料不需要改任何代码 |

**建议的写作规范**（直接决定检索质量）：

```markdown
# 曾侯乙编钟

## 概况
战国早期大型礼乐重器，1978 年出土于湖北随州擂鼓墩……

## 工艺
采用分范合铸，共 65 件，总重 2567 公斤……
```

- 一级标题写文物名，二级标题写「概况 / 年代 / 工艺 / 展厅位置」这类主题
- 一段讲一件事，别写成一大坨
- 事实要具体（年代、尺寸、出土地、展厅），这些词是检索能命中的关键

## 前端接入（实现「重启恢复对话」三步）

1. 把 `session_id` 存进 `SharedPreferences`，替代现在的每次 `UUID.randomUUID()`
   （`MainActivity.java:50`）。
2. 启动时调 `GET /api/sessions/{id}/messages`，把返回的 `messages` 按 `content` 回填到
   `ChatUiManager` 的列表。
3. 用户清空对话时调 `DELETE /api/sessions/{id}`，然后换一个新编号。

`/api/chat` 和 `/api/voice` 的调用方式完全不用改。

### 可选：在回答下面挂"资料链接"

如果想要"回答有出处"的效果（答辩时很加分），只需接流式接口：

1. 改调 `/api/chat/stream`（SSE），用 `fetch` + `getReader()` 解析；
2. 收到 `meta` 事件时，把 `sources_detail` 存起来；
3. 回答吐完后，在气泡下面渲染一排小胶囊，点击打开 `url`：

```
[ 越王勾践剑 · 出土与年代 ]  [ 越王勾践剑 · 工艺 ]
```

`url` 是相对路径，拼上 `http://<后端地址>` 就能用 WebView 打开。
`/api/chat`（非流式）为了保持兼容**没有**加这个字段，所以想要链接就得走流式。
调试台 `/debug` 里已有这个效果的参考实现（`static/debug.html` 的 `setSourcePills`）。

## GET /api/kb/search（资料库检索，不经过任何模型）

供 APP「资料库」页面使用：观众不提问，直接按关键词或条件翻资料，**不消耗任何模型额度**。

| 参数 | 说明 |
|---|---|
| `q` | 关键词；中文按 2~3 字滑窗切分，命中数 ≥ `min(2, 片段数)` 才算相关（所以"故宫"这种两字词也能搜到） |
| `kind` | `museum` / `artifact`，留空=全部 |
| `province` | 省份，如 `湖北省` |
| `category` | 文物类别，如 `青铜器`（只有文物卡有这个字段） |
| `limit` / `offset` | 分页，默认 30 / 0，`limit` 上限 200 |

返回：

```json
{
  "query": "青铜剑", "total": 2, "offset": 0, "limit": 20,
  "items": [{
    "title": "越王勾践剑",
    "path": "全国博物馆资料馆/artifacts/湖北省/湖北省博物馆/越王勾践剑.md",
    "kind": "artifact", "province": "湖北省", "museum": "湖北省博物馆",
    "category": "青铜器", "snippet": "…", "score": 13
  }],
  "facets": {
    "provinces": [{"name": "北京市", "count": 68}],
    "categories": [{"name": "青铜器", "count": 47}]
  }
}
```

`facets` 是按"关键词 + 类型"统计出的筛选项与数量，会随查询变化；
前端直接拿它渲染下拉框，不必再单独请求一次。

## GET /api/kb/doc

参数 `path`（相对 `knowledge_base/` 的路径，必填），返回：

```json
{"title": "越王勾践剑", "path": "…", "text": "# 越王勾践剑\n\n…",
 "kind": "artifact", "province": "湖北省", "museum": "湖北省博物馆", "category": "青铜器"}
```

`path` 里带 `../` 之类的越权路径会被 404 挡住。

## GET /api/kb/filters

返回与 `/api/kb/search` 相同的 `facets` 结构，供页面初始化时一次拿到筛选项。

## 已知问题

### 知识库规模与覆盖

`knowledge_base/全国博物馆资料馆/` 现有 **616 份**资料（327 个一级博物馆卡 + 288 件文物卡），
检索链路已就绪。资料没有覆盖到的馆，问答会走「资料库里暂时没有这部分内容」的兜底话术——
这是预期的行为，不是接口问题。扩充资料只需往目录里加 `.md`，重启后索引会增量同步。

### 部署必须单进程

向量库是**进程内**数据库，同一个索引目录只能被一个进程打开。
所以**不要用 `uvicorn --workers N`（N>1）**，默认的 1 就是对的。
误开了多进程也不会崩：打不开索引的那个进程会自动退回关键词模式，
日志里会写 `[向量库] 初始化失败：… → 检索退回关键词模式`。
