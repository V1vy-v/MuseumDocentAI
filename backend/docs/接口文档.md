# 后端接口文档

> 简要说明各接口的用法。设计思路见同目录《记忆系统与指代消解方案.md》。
>
> 两个自测入口：
> - **http://127.0.0.1:8000/docs** —— 交互式接口文档（能点着发请求、传文件）
> - **http://127.0.0.1:8000/debug** —— 调试台，能连续多轮对话并看到
>   指代消解结果、滚动摘要、token 明细（这些东西 `/docs` 里看不到，见 `backend/README.md`）

## 启动

```bash
cd backend
uvicorn app.main:app --reload --port 8000
```

## 通用约定

- 所有接口前缀 `/api`，请求与响应均为 JSON（UTF-8）。
- 时间字段是 **UTC 的 ISO8601**，例如 `2026-10-11T14:00:18+00:00`。
- 服务启动时会自动创建数据库 `backend/data/chat.db`（已 gitignore），并清理超过 7 天未活动的会话。

### 错误格式

出错时返回非 2xx，响应体**平铺**为：

```json
{
  "error": "session not found",
  "hint": "该会话不存在或已被清理"
}
```

- `error` 给开发看（保留原始异常信息），`hint` 给用户看（可直接显示在界面上）。
- 前端 `ApiClient.handleResponse` 用 `json.has("error")` 判断即可。
- 未被业务代码覆盖的错误（例如访问了不存在的路由）仍是 FastAPI 默认的
  `{"detail": "Not Found"}`。

> 实现说明：FastAPI 的 `HTTPException(detail={...})` 默认会再包一层 `detail`，
> 所以 `app/main.py` 注册了一个异常处理器把它摊平。
> 改这个格式前请先确认前端 `ApiClient` 和 `schemas/chat.py` 的 `ErrorResponse`。

## 接口一览

| 方法 | 路径 | 用途 | 依赖模型 |
|---|---|---|---|
| GET | `/api/health` | 健康检查 | 否 |
| POST | `/api/chat` | 文本问答 | 是 |
| POST | `/api/chat/stream` | 流式问答（SSE） | 是 |
| POST | `/api/voice` | 语音问答 | 是 |
| POST | `/api/sessions` | 新建会话 | 否 |
| GET | `/api/sessions` | 历史会话列表 | 否 |
| GET | `/api/sessions/{id}/messages` | 拉取历史 | 否 |
| DELETE | `/api/sessions/{id}` | 清除会话 | 否 |

「依赖模型」= 需要 `backend/.env` 里配置有效的 `DEEPSEEK_API_KEY`，否则返回 502。

## POST /api/chat

文本问答。**入参和回参自始至终未变，前端无需改动。**

请求：

```json
{
  "question": "它是什么年代的？",
  "session_id": "任意字符串，同一会话复用同一个值"
}
```

响应：

```json
{
  "answer": "越王勾践剑是春秋晚期的文物，距今大约两千五百年左右。",
  "sources": ["示例_越王勾践剑"]
}
```

说明：

- `session_id` **不需要预先创建**。首次写入时服务端会自动建会话，所以前端照旧自己生成 UUID 即可。
- 服务端处理顺序：取上下文 → **指代消解** → 用消解后的问句检索 → 生成回答。
  所以「它」这类代词能正确指向上一轮讲的文物；消解结果会存进库，可用下面的历史接口查看。
- 检索不到资料时会走防幻觉分支，回答「馆内资料暂未收录」而不是编造。

## POST /api/chat/stream

**流式问答（SSE）**。请求体和 `/api/chat` 完全一样，只是响应变成一条事件流。

```json
{"question": "它是什么年代的？", "session_id": "任意字符串"}
```

响应头：

```
Content-Type: text/event-stream; charset=utf-8
Transfer-Encoding: chunked
Cache-Control: no-cache
```

事件格式是标准 SSE（`event:` 行 + `data:` 行，**空行分隔事件**）：

| 事件 | 时机 | data |
|---|---|---|
`meta` | 最先 | `{"session_id": "...", "sources": ["示例_越王勾践剑"], "resolved": "越王勾践剑是什么年代的？"}` |
`delta` | 多次 | `{"text": "越王"}` —— 文本增量，客户端往气泡后面追加 |
`done` | 正常结束 | `{"answer": "完整回答", "usage": {"prompt_tokens": 279, ...}}` |
`error` | 中途出错 | `{"error": "...", "hint": "AI 服务暂时不可用，请稍后再试"}` |

原始报文长这样：

```
event: meta
data: {"session_id":"s1","sources":["示例_越王勾践剑"],"resolved":"..."}

event: delta
data: {"text":"越王"}

event: delta
data: {"text":"勾践剑"}

event: done
data: {"answer":"越王勾践剑是春秋晚期...","usage":{"prompt_tokens":279}}
```

**要点**：

1. **`meta` 先到（实测 0.02s）**，这时模型还没开始生成——界面上可以先显示来源和消解结果。
2. **`error` 是事件，不是 HTTP 状态码**。首块一旦发出，响应头就定了，后面改不了状态码，
   所以错误只能作为事件报给前端。**客户端必须处理这个事件**，不能只看 HTTP 200。
3. **`/api/chat` 一点没变**，两个接口共用同一套前置逻辑（压缩 → 取上下文 → 消解 → 检索），
   所以行为一致。
4. 客户端中途断开时，**已经生成的部分会被落库**，这一轮不会丢。

**实测收益**（2026-10，本地直连）：

```
meta 到达        0.02s
第一个 delta     3.32s    ← 观众看到第一个字的时刻
最后一个事件     7.19s
delta 分布       59 块横跨 3.14s（真流式，没有被中间层缓冲）
```

对比非流式：同样的回答必须等整段生成完才能返回。长回答（约 3000 字）实测
**首字 1.85~3.03s vs 整段 24~30s**，感知延迟降约 10 倍，总时长不变。

**命令行自测**（`-N` 很关键，否则 curl 自己会缓冲）：

```bash
curl -N -X POST http://127.0.0.1:8000/api/chat/stream \
  -H "Content-Type: application/json" \
  -d '{"question":"越王勾践剑是什么时期的文物？","session_id":"demo"}'
```

> ⚠️ **浏览器端不能用 `EventSource`**：它只支持 GET，而这里的问句要走 POST 请求体。
> 要用 `fetch()` + `response.body.getReader()` 手动解析 SSE。
> 解码时 `TextDecoder` 必须带 `{stream: true}`，否则一个汉字被切到两个数据块里会变乱码。

> ⚠️ **中间有缓冲型代理时流式会失效**：后端日志显示"0.02s 就发了首块"，
> 但客户端要等整段才收到。验证方法是对照首块发送时间与客户端首个 `delta` 的到达时间。
> 模拟器走 `10.0.2.2`、或经过 Clash 这类代理时尤其要实测确认。

## POST /api/voice

语音问答：录音进去，回答文字 + 播报语音出来。

请求：`multipart/form-data`

| 字段 | 类型 | 说明 |
|---|---|---|
| `audio` | 文件 | WAV 录音（16kHz / 16bit / 单声道实测可用） |
| `session_id` | 文本 | 会话编号 |

响应：

```json
{
  "question": "你好，请问博物馆今天开放吗？",
  "answer": "您好！关于今天的开放时间……",
  "sources": [],
  "audio_base64": "UklGRi…"
}
```

说明：

- `question` 是语音识别出的文字，界面上可以显示「我听到的是…」。
- `audio_base64` 是 WAV 的 base64，空串表示不播报。
- 录音为空返回 400。

## POST /api/sessions

新建会话。**可选接口**——不调也能正常问答，只有想让服务端发号时才需要。

请求体可以完全省略，也可以指定编号：

```json
{"session_id": "my-own-uuid"}
```

响应：

```json
{
  "session_id": "my-own-uuid",
  "created_at": "2026-10-11T14:00:18+00:00",
  "existed": false
}
```

- `existed: true` 表示该编号已存在，直接沿用（不会清空它的历史）。
- 传空串或空白等同于不传，服务端会生成一个新的。
- **新建的空会话不会出现在下面的历史列表里**，发出第一条消息后才会出现
  （和通用聊天应用的行为一致）。

## GET /api/sessions

列出历史会话，按最近活跃倒序。界面左侧那种"对话列表"就用它。

查询参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `limit` | 50 | 最多返回几条 |
| `include_empty` | `false` | 是否连"建了但没发过消息"的空会话一起返回 |

响应：

```json
{
  "count": 2,
  "sessions": [
    {
      "session_id": "s-newer",
      "title": "青铜展厅怎么走？",
      "created_at": "2026-10-12T13:29:52+00:00",
      "updated_at": "2026-10-12T13:29:52+00:00",
      "message_count": 2
    },
    {
      "session_id": "s-kept",
      "title": "越王勾践剑是什么时期的文物？",
      "created_at": "2026-10-12T13:29:35+00:00",
      "updated_at": "2026-10-12T13:29:40+00:00",
      "message_count": 4
    }
  ]
}
```

- `title` 取首问，供列表展示；空会话没有标题。
- `updated_at` 是最近一次活动时间，列表按它倒序；精度只到秒，同一秒内按创建顺序兜底，
  所以**顺序是稳定的**（不会每次刷新都换位置）。
- 只返回展示需要的字段，**不含消息正文**，列表接口不会把整个会话拖出来。

## GET /api/sessions/{id}/messages

拉取某会话的完整历史。**APP 重启后用它把对话界面回填。**

响应：

```json
{
  "session_id": "e2e-lifecycle-001",
  "title": "越王勾践剑是什么时期的文物？",
  "summary": "",
  "created_at": "2026-10-11T14:05:00+00:00",
  "updated_at": "2026-10-11T14:05:12+00:00",
  "messages": [
    {"role": "user", "content": "越王勾践剑是什么时期的文物？",
     "sources": [], "created_at": "…", "resolved": "越王勾践剑是什么时期的文物？"},
    {"role": "assistant", "content": "越王勾践剑是春秋晚期的文物……",
     "sources": ["示例_越王勾践剑"], "created_at": "…", "resolved": ""},
    {"role": "user", "content": "它是什么年代的？",
     "sources": [], "created_at": "…", "resolved": "越王勾践剑是什么年代的？"}
  ]
}
```

字段说明：

| 字段 | 说明 |
|---|---|
| `title` | 取首问，供历史列表展示 |
| `summary` | 长对话滚动摘要；对话还短时是空串 |
| `messages[].content` | **用户原话**，未经改写 |
| `messages[].resolved` | 指代消解后的问句，**诊断用**，界面展示请用 `content` |
| `messages[].sources` | 该轮回答引用的资料标题 |
| `messages[].tokens` | 这条消息占多少 token（估算值，**诊断用**：上下文窗口就是按它算的） |
| `last_prompt_tokens` | 最近一次请求的真实 `prompt_tokens`（来自服务端 `usage`，**诊断用**） |

会话不存在（或已被 TTL 清理）返回 **404**。

---

## DELETE /api/sessions/{id}

清除会话及其全部消息。

```json
{"ok": true, "deleted": true}
```

- **幂等**：会话不存在时返回 `deleted: false`，不报错。前端本地存了过期编号时不必特殊处理。
- 消息随会话级联删除。

---

## 前端接入（实现「重启恢复对话」三步）

1. 把 `session_id` 存进 `SharedPreferences`，替代现在的每次 `UUID.randomUUID()`
   （`MainActivity.java:50`）。
2. 启动时调 `GET /api/sessions/{id}/messages`，把返回的 `messages` 按 `content` 回填到
   `ChatUiManager` 的列表。
3. 用户清空对话时调 `DELETE /api/sessions/{id}`，然后换一个新编号。

`/api/chat` 和 `/api/voice` 的调用方式完全不用改。
