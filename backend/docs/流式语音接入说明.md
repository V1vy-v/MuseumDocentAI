# 流式语音（with_audio）接入说明

> 面向：前端（安卓 APP / Web）。
> 后端实现：`app/api/chat.py`（事件编排）、`app/services/speech.py`（切句 + 后台合成）。
> 接口总览见 [`接口文档.md`](./接口文档.md)。

## 1. 一句话说明

`POST /api/chat/stream` 新增可选参数 **`with_audio: true`**：服务端在生成文字的同时，
**按句**合成语音并顺流推给客户端。客户端一次请求就能做到「文字边出、声音边播」，
不必等整段回答结束再调 `/api/tts`。

**不传这个参数时，行为和以前完全一样**，老客户端零改动。

## 2. 为什么需要它（实测数据）

提问「给我讲讲越王勾践剑」，两条路径对比：

| 时间点 | 旧路径（等全文 → 整段合成） | 新路径（with_audio） |
|---|---|---|
首个文字 | 0.95 s | 0.95 s |
文字结束 | 1.39 s | 1.46 s |
**声音可以开始播** | **6.33 s** | **3.49 s** |
最后一句音频到达 | — | 10.84 s |
音频 | 1 段（整段） | 5 段（按句） |

**声音提前了 2.84 秒。**

原因在 TTS 的耗时构成：实测 `TTS ≈ 0.7s + 35ms/字`（17 字 1.30s、55 字 2.61s、124 字 5.01s）。
等整段回答（132 字）再合成要 4.95 秒；按句合成时第一句只要 1 秒多。

而**合成速度大约是播放速度的 4 倍**（35ms/字合成 vs 250ms/字播放），
所以只要第一句出来了，后面的句子一定能在播放期间合成完，不会断档。

## 3. 请求

请求体和以前一样，只多一个字段：

```json
{
  "question": "它是什么年代的？",
  "session_id": "任意字符串",
  "with_audio": true
}
```

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
`question` | string | 必填 | 问题文本 |
`session_id` | string | 必填 | 会话编号 |
`retrieval` | string | `""` | `""`/`"auto"` 自动、`"keyword"` 只用关键词、`"vector"` 只用向量 |
`with_audio` | bool | **`false`** | 是否顺带合成语音 |

## 4. 响应：多了两个事件

原有事件（`meta` / `delta` / `done` / `error`）**字段和含义都没变**。新增：

| 事件 | data | 说明 |
|---|---|---|
`audio` | `{"index": 0, "format": "wav", "audio_base64": "UklGR..."}` | 一句话的音频 |
`audio_done` | `{"count": 5, "error": ""}` | 语音已经全部推完；`error` 非空表示合成失败的原因 |

### 事件顺序（**这一点最容易踩坑**）

```
meta → (delta | audio)* → done → audio* → audio_done
```

注意两件事：

1. **`done` 在音频之前**。它表示「文字已经完整」，客户端应立即把输入框放开、
   结束"生成中"状态——不要因为等音频而让用户以为还在生成。
2. **收到 `done` 之后流还没结束**，要**继续读**，直到 `audio_done` 或连接关闭。
   如果客户端在 `done` 时就关闭连接，后面的音频会全部丢掉（服务端也会停止合成）。

### 实际报文

```
event: meta
data: {"session_id":"s1","sources":["越王勾践剑"],"sources_detail":[…],"resolved":"…"}

event: delta
data: {"text":"越王勾践剑是"}

event: audio
data: {"index":0,"format":"wav","audio_base64":"UklGRiQAAABXQVZF…"}

event: delta
data: {"text":"春秋晚期的越国青铜剑。"}

event: delta
data: {"text":"它出土于湖北江陵望山一号楚墓。"}

event: done
data: {"answer":"越王勾践剑是春秋晚期的越国青铜剑。它出土于…","usage":{…}}

event: audio
data: {"index":1,"format":"wav","audio_base64":"UklGRiQ…"}

event: audio_done
data: {"count":2,"error":""}
```

## 5. 客户端接入要点

### 5.1 按 `index` 顺序播放

`index` 从 0 递增，**必须按序号播放**。服务端是顺序合成的，正常情况下到达即有序，
但客户端仍应自己维护一个按 `index` 排序的队列——这样即使某句先到也乱不了。

### 5.2 播放队列（关键）

不要「收到一句就打断上一句」，而要**排队**：

```
收到 audio → base64 解码 → 塞进队列 → 若当前没有在播，出队播放
播放结束(onCompletion/onended) → 继续出队
收到 audio_done → 不再期待新音频，队列播完即止
```

### 5.3 用户打断

用户点「停止」时要**三件事都做**，缺一件就会继续出声：

1. 关闭 SSE 连接（服务端会因此停止后续合成）；
2. 清空播放队列；
3. 停止当前播放器并释放。

### 5.4 不要重复播

用了 `with_audio` 就**不要再调 `/api/tts`**，否则同一段回答会播两遍。
`with_audio` 是 `/api/tts` 在流式场景下的替代品；非流式场景（`/api/chat`、`/api/voice`）
仍然用 `/api/tts` 或响应里的 `audio_base64`。

### 5.5 Android 伪代码

```java
// 1) 解析：和现有 streamOnce 一样，只是多两个 case
switch (event) {
    case "audio": {
        JSONObject j = new JSONObject(payload);
        int index = j.optInt("index", 0);
        byte[] wav = Base64.decode(j.optString("audio_base64", ""), Base64.DEFAULT);
        speechQueue.offer(index, wav);          // 按 index 排序的队列
        playNextIfIdle();
        break;
    }
    case "audio_done":
        audioFinished = true;                    // 队列播完就不再等
        break;
}

// 2) 播放：MediaPlayer 单实例复用，避免并发
private void playNext() {
    byte[] wav = speechQueue.poll();
    if (wav == null) return;
    File f = new File(cacheDir, "tts_" + (seq++) + ".wav");
    try (FileOutputStream out = new FileOutputStream(f)) { out.write(wav); }
    player.reset();
    player.setDataSource(f.getAbsolutePath());
    player.setOnCompletionListener(mp -> playNext());
    player.prepare();
    player.start();
}
```

> 播放器选择：`MediaPlayer` 最简单；要做低延迟无缝衔接可用 `AudioTrack`
> （需要自己解析 WAV 头，16bit 单声道 16kHz → 直接可播）。

### 5.6 Web 伪代码

```js
const queue = [];              // [{index, url}]
let playing = false;

function enqueue(index, base64) {
  queue.push({ index, url: 'data:audio/wav;base64,' + base64 });
  queue.sort((a, b) => a.index - b.index);
  playNext();
}

function playNext() {
  if (playing || !queue.length) return;
  playing = true;
  const item = queue.shift();
  const audio = new Audio(item.url);
  audio.onended = () => { playing = false; playNext(); };
  audio.play().catch(() => { playing = false; });
}
```

## 6. 时序示意（实测）

```
0.00s  提问
0.95s  首个文字出现            ← 观众开始读
1.46s  文字结束（done）        ← 输入框放开，但不要关流
3.49s  第一句音频到达          ← 可以开始播（旧路径此时还要等 2.8 秒）
       …播放中，后续句子陆续到达（平均每 1.8s 一句，而每句要播约 9s，追得上）
10.84s audio_done（5 句全部到达）
       …继续播到结束
```

## 7. 失败与降级

| 情况 | 表现 | 客户端应怎么做 |
|---|---|---|
没配置 TTS | `audio_done {count: 0, error: "未配置 TTS 服务"}` | 静默降级：只显示文字，不弹错误框 |
合成中途失败 | 之前已合成的句子照常推送，`audio_done.error` 带原因，`count` 是实际句数 | 播完已到的，记日志即可 |
文字生成失败 | 先收到 `error` 事件（和以前一样） | 按原来的错误处理 |

**任何情况下文字回答都不受影响**——语音是附加能力，失败不会让 `/api/chat/stream` 报错。

## 8. 兼容性

| 场景 | 影响 |
|---|---|
老客户端（不传 `with_audio`） | 无变化，不会出现 `audio` / `audio_done` 事件 |
只解析 `meta`/`delta`/`done` 的客户端 | 忽略未知事件即可（SSE 本来就该这么做） |
`/api/chat`（非流式） | **完全没动**，仍是 `{answer, sources}` |
`/api/voice` | **完全没动**，仍是「识别 + 回答 + 整段音频」一次返回 |

## 9. 自测

```bash
curl -N -s -X POST http://127.0.0.1:8000/api/chat/stream \
  -H "Content-Type: application/json; charset=utf-8" \
  -d '{"question":"给我讲讲越王勾践剑","session_id":"demo","with_audio":true}'
```

预期：先看到 `meta`、若干 `delta`、`done`，然后是若干 `audio`，最后 `audio_done`。
把某个 `audio_base64` 拷出来存成 `.wav` 就能直接播放，用来确认音频本身没问题。

**注意**：不要把 `with_audio` 打到 `/api/chat`（非流式）上，那个接口不认这个字段。

## 10. 已知限制与可调参数

| 项 | 现状 | 说明 |
|---|---|---|
音频体积 | 144 字 → 约 1515 KB WAV，base64 后传输约 2 MB | WAV 未压缩，体积天然大。将来要给音频换压缩格式（如 mp3）需要同时改 `/api/tts` |
首句长度 | 后端常量 `speech._MAX_CHARS = 40` 字 | 首句越短发声越早；调小能再快几百毫秒，但句子切太碎听起来不连贯 |
整轮上限 | `speech._MAX_TOTAL = 600` 字 | 防止模型输出超长把 TTS 额度吃光；超出的部分不合成 |
短回答收益小 | 只有 1 句时和旧路径几乎一样 | 因为只有一个"第一句" |
TTS 调用次数 | 从 1 次变成"每句一次" | 每句有约 0.7s 固定开销，总耗时略增；换来的是首音大幅提前 |
