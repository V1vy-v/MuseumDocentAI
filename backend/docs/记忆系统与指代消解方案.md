## 一、现状盘点

### 1.1 后端接口与调用链

后端当前只有 3 个接口（`app/main.py`）：

| 接口 | 文件 | 作用 |
|---|---|---|
| `POST /api/chat` | `app/api/chat.py` | 文本问答 |
| `POST /api/voice` | `app/api/voice.py` | 语音问答（ASR → 回答 → TTS） |
| `GET /api/health` | `app/main.py` | 健康检查 |

`POST /api/chat` 的实际执行顺序：

```python
sources = rag.retrieve(req.question)                        # ① 先检索
history = memory.recall(req.session_id)                     # ② 再取历史
answer  = llm_client.chat_reply(question, history, sources) # ③ 生成回答
memory.remember(session_id, "user", req.question)           # ④ 后写入历史
memory.remember(session_id, "assistant", answer)
```

`POST /api/voice` 在此基础上前后各加一步（ASR 识别、TTS 合成），中间三步结构与 chat 完全一致。

### 1.2 记忆系统现状（`app/services/memory.py`，共 26 行）

| 维度 | 现状 | 问题 |
|---|---|---|
| 存储位置 | 进程内 `defaultdict(list)` | 服务重启全部丢失 |
| 数据结构 | 扁平列表 `[{"role","content"}]` | 无 id、无时间戳、无来源、无元数据 |
| 容量控制 | 滑动窗口 `MAX_TURNS = 20`（条） | 超出部分永久丢失；按「条」切会从一轮问答中间切断 |
| 会话隔离 | 仅以 `session_id` 作字典 key | 无过期、无清理、无数量上限，空会话持续堆积 |
| 长对话压缩 | 无 | 超出窗口的信息不可恢复 |
| 对外 API | `remember(session_id, role, content)`<br>`recall(session_id) -> list` | —— |

`llm_client.chat_reply` 内部又做了一次截断 `history[-10:]`，因此实际送入模型的上文约为最近 10 条消息。

### 1.3 指代消解现状

**完全没有实现。** 全仓库检索 `指代` / `消解` / `coreference` 仅命中 `memory.py` 第 5 行的一句注释：

> 后续升级方向：存到文件/数据库、指代消解、长对话摘要压缩。

`backend/README.md` 的目录说明中已将「指代消解（"它"指什么）」列入角色 D 的 `memory.py` 职责。

### 1.4 会话持久化现状

后端**零持久化**。前端 `MainActivity.java` 第 50 行使用 `UUID.randomUUID().toString()` 生成 `session_id`，即：

> **每次启动 APP 都是一个全新会话**，当前的 `session_id` 实质只是「本次运行期间的内存字典 key」。

### 1.5 三个必须先修的问题

#### 问题 A（最关键）——检索发生在指代消解之前

`rag.retrieve()` 对**原始问题**做 2~3 字滑窗关键词匹配，且要求命中数 `hits >= 2`（`rag.py` 第 41 行）。当用户第二句问「它是什么年代的？」时：

1. 切出的词片为 `它是 / 是什么 / 什么年 / 么年代 / 年代` 等，与《越王勾践剑》正文几乎零命中；
2. `hits < 2` → 返回空列表；
3. `sources` 为空 → `llm_client` 走「本次没有检索到相关馆内资料」分支 → 模型被指示回答 `NO_KNOWLEDGE_REPLY`（"抱歉，这个问题馆内资料暂未收录…"）。

**结论：仅新增一个「代词改写函数」不足以解决问题，必须把消解步骤插入到 ①② 之间，并让 RAG 用消解后的问句检索。** 这是本次改造中顺序上最关键的一处调整。

#### 问题 B——会话窗口可能从「轮」中间切断

`MAX_TURNS = 20` 按「条」计数。滑窗后 `history` 很可能以 `assistant` 开头（丢失了对应的提问），模型会看到一个没有问题的回答；随后 `llm_client` 再切一次 `[-10:]`，二次截断语义不明确。改造时应改为**按轮（user + assistant 成对）对齐**截断。

#### 问题 C——前端不配合则持久化无法体现

后端把会话存入数据库，但 APP 每次重启更换新 UUID，用户重启后既看不到旧对话，多轮记忆也归零。因此持久化必须与前端联动：`session_id` 落 `SharedPreferences`，启动时拉取历史回填界面。

## 二、总体设计

### 2.1 改造后的调用链

```
app/api/chat.py  voice.py
      │
      ├─ memory.get_context(session_id)          ← 新增：一次取回 summary + 最近若干轮
```

### 2.3 存储选型说明

| 方案 | 结论 | 理由 |
|---|---|---|
| 内存字典（现状） | ✗ | 重启即丢，不满足持久化要求 |
| JSON 文件 | ✗ | 并发写有竞态、需全量重写、无法按条件查询 |
| **SQLite** | ✓ **采用** | 标准库免安装、单文件零运维、支持索引/事务/级联删除，适合课程与演示环境 |
| PostgreSQL / MySQL | ✗ | 需额外部署运维，本项目规模无必要 |

## 三、会话持久化设计

### 3.1 表结构（`app/services/store.py`）

```sql
PRAGMA journal_mode = WAL;      -- 读写并发，避免读被写阻塞
PRAGMA busy_timeout = 5000;     -- 并发写时等待而非直接报 database is locked
PRAGMA foreign_keys = ON;       -- 让级联删除生效

CREATE TABLE IF NOT EXISTS sessions (
    session_id   TEXT PRIMARY KEY,
    created_at   TEXT NOT NULL,          -- ISO8601 UTC
    updated_at   TEXT NOT NULL,
    summary      TEXT DEFAULT '',        -- 长对话滚动摘要
    summary_upto INTEGER DEFAULT 0,      -- 摘要已覆盖到 messages.id
    title        TEXT DEFAULT ''         -- 取首问，供前端历史列表展示
);

CREATE TABLE IF NOT EXISTS messages (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id  TEXT NOT NULL REFERENCES sessions(session_id) ON DELETE CASCADE,
    role        TEXT NOT NULL,           -- user / assistant
    content     TEXT NOT NULL,           -- 用户原话，不做任何改写（保真）
    resolved    TEXT DEFAULT '',         -- 消解后的独立问句，仅 user 消息有
    sources     TEXT DEFAULT '[]',       -- JSON 数组，仅 assistant 消息有
    created_at  TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_msg_session ON messages(session_id, id);
```

### 3.2 三个易踩的工程细节

1. **数据库连接不可全局共享。**
   FastAPI 的 `def`（非 `async`）端点运行在线程池中，多请求对应多线程。做法：用 `@contextmanager` 每次调用开一条连接（SQLite 建连接开销极低），或用 `threading.local()` 复用连接。切勿在模块级创建单一连接并跨线程使用。

2. **写事务要短。**
   `remember()` 内的两条 insert 加一条 `sessions.updated_at` update 应放在同一个 `with conn:` 事务中，避免半写入状态。

3. **DB 路径集中配置。**
   在 `config.py` 中定义 `DB_PATH = BASE_DIR / "data" / "chat.db"`，启动时 `mkdir(parents=True, exist_ok=True)`；`.gitignore` 增加 `backend/data/`，避免把本地数据库提交进仓库。

### 3.3 兼容策略

`memory.remember()` 与 `memory.recall()` 的**签名和返回格式保持不变**，仅内部实现改为读写 SQLite。这样 `chat.py` / `voice.py` 的改动面被压到最小，也保证角色 C 的 `rag.py` 不受影响。

`recall()` 的返回值仍是 `[{"role", "content"}, ...]`，因此现有 `llm_client.chat_reply()` 无需立刻适配即可跑通。

### 3.4 生命周期治理

| 项 | 配置 | 说明 |
|---|---|---|
| 单会话消息上限 | `MAX_MSG_PER_SESSION = 500` | 超出后丢弃最早的非摘要消息，兜底防膨胀 |
| 会话 TTL | `SESSION_TTL_DAYS = 7` | 启动时清理一次过期会话 |
| 清理时机 | `main.py` 的 `startup` 事件 | **不要**每个请求都跑清理，成本无必要 |

## 四、记忆系统升级设计

### 4.1 分层上下文（替代裸滑动窗口）

新增接口，一次取回模型所需全部上文：

```python
def get_context(session_id: str) -> dict:
    """返回 {"summary": str, "history": [...], "recent_sources": [...]}"""
```

`llm_client.chat_reply()` 的消息拼装方式变为：

```
system（人设 + 摘要 + 检索资料）
  + 最近若干轮原文（按轮对齐）
  + 本轮问题
```

> 摘要**并入同一个 system 消息**，而不是新增一条 system——不同模型对多条
> system 消息的容忍度不一致，合并最稳。

### 4.2 长对话滚动摘要（按 token 触发）

**与常见 agent 的 compact 有一个关键区别：摘要只是数据库之上的一层"视图"。**
它只改变"模型看到什么"，**不删除任何原文**——`GET /api/sessions/{id}/messages`
仍能完整取回全部对话，前端照旧完整展示。（compact 通常会把原文从上下文里替换掉。）

触发依据是 **token 而不是消息条数**：

- 一条 500 字的资料和一句"嗯"都算一条消息，按条数切窗口完全不准；
- token 才是真正的资源约束（成本与上下文上限）。

实现要点：

1. **不需要分词器。** mimo 接口在 `usage` 里返回真实用量（`prompt_tokens` 等），
   安全阀直接用服务端数字；日常判断用中文经验值 `1 汉字 ≈ 1 token`
   （实测 13 字 → 15 `prompt_token`，含 chat 模板开销）。估算值随消息落库，
   窗口与触发都只是一次带索引的 `SUM` 查询。
   不用 `tiktoken`：那是 OpenAI 的词表，对 mimo 本来就不准，还要加依赖。
2. **边界对齐用"往前补"而不是"往后砍"。** 预算恰好装下奇数条消息时，
   往后砍会一次丢掉半轮问答（极端情况丢掉一半窗口）；往前补只多带一条消息。
3. **摘要增量合并。** 每次只把「已滑出窗口、且 `id > summary_upto`」的那一段
   并入已有摘要，而不是重头总结；合并范围写回 `summary_upto`。
4. **摘要是尽力而为。** `summarize()` 失败只记录原因并跳过，绝不影响正常问答，
   下一轮会再触发。

> **性能约束**：多数请求什么都不做（一次 `SUM` 查询），只有累积跨过阈值时才多
> 一次模型调用。语音链路已有 ASR + 生成 + TTS 三次串行调用，延迟预算很紧。

**固有的代价**：增量摘要会累积误差——每轮合并都在上一次摘要之上再压缩，聊得特别
久之后早期细节会逐渐模糊。这是滚动摘要的固有问题，不是实现缺陷；要更高保真就得
改成对原文做分层索引/检索，那是另一个量级的工作。

### 4.3 配置项（`app/core/config.py`）

```python
DB_PATH                = BASE_DIR / "data" / "chat.db"
RECENT_TOKEN_BUDGET    = 1200   # 最近多少 token 的对话原样喂给模型
SUMMARY_TRIGGER_TOKENS = 2400   # 窗口外累积超过此值才压缩一次
SUMMARY_MAX_CHARS      = 400    # 摘要文本长度上限
PROMPT_TOKEN_ALERT     = 6000   # 整个提示词超过此值就告警（压缩已不够用）
MAX_MSG_PER_SESSION    = 500
SESSION_TTL_DAYS       = 7
```

> 早期设计里的 `RECENT_TURNS` / `SUMMARY_TRIGGER` / `SUMMARY_KEEP_TAIL` 已全部删除：
> 前两个换成 token 预算；第三个和"窗口大小"表达的是同一件事（重复配置），
> 留着会让"改窗口"时容易漏改。

## 五、指代消解设计

新建 `app/services/coreference.py`。接口设计为**纯函数**，便于单元测试：

```python
def needs_resolution(question: str) -> bool:
    """判断问句是否含需要消解的代词/指示词"""

def resolve(question: str, history: list, focus: str = "") -> tuple[str, dict]:
    """返回 (消解后的问句, {"changed": bool, "antecedent": str, "method": "rule|llm|none"})"""
```

### 5.1 第一级：焦点追踪 + 规则改写（零 API 成本，覆盖约 80% 场景）

核心思路不是「解析代词」，而是维护一个**话题焦点（focus）**——即上一轮到底在聊哪件文物。

**焦点如何确定：**

- 用户提问命中知识库标题时记下该书物（`knowledge_base/*.md` 的 stem 去掉 `示例_` 前缀，如"越王勾践剑"）；
- 同时记录该轮 `rag.retrieve()` 返回的 `sources` 标题作为候选；
- 焦点随会话推进更新，存入会话状态。

**代词表（语音场景必须包含 ASR 同音字，这一点很关键）：**

```python
PRONOUNS = [
    "它", "他", "她", "牠",          # 语音识别常把「它」写成「他/她」
    "这个", "那个", "这件", "那件", "这只", "那把",
    "此", "该", "刚才说的", "上面提到的", "这件文物",
]
```

**改写方式**：命中代词时，将其替换为焦点实体：

```
输入：「它是什么年代的？」
焦点：越王勾践剑
输出：「越王勾践剑是什么年代的？」
```

**歧义保护（必须做）**：以下情况**不改写**，交由第二级处理或按原句处理，避免瞎猜导致答非所问：

- 焦点为空（会话第一句就说「它」）；
- 问句中出现「都 / 分别 / 两个 / 这几个」等暗示多实体的词；
- 历史中存在多个同等置信度的候选实体。

### 5.2 第二级：LLM 改写兜底（按需触发）

仅当第一级判定「含代词但焦点不唯一」时触发一次极短 prompt：

```
把观众这句话里的代词替换成上文明确的对象，只输出改写后的问句，不要解释。
上文：<最近 2 轮对话>
本句：<用户原句>
```

选用 `mimo-v2.6-flash`，限制 `max_tokens`。

> **可靠性约束**：必须设超时并做失败降级——改写失败即退回原句，**绝不能让消解环节把主流程搞挂**。语音问答对延迟敏感，此处应计入总耗时预算。

### 5.3 接口层的顺序调整（本次改造的核心）

```python
ctx = memory.get_context(session_id)
resolved, info = coreference.resolve(req.question, ctx["history"])
query   = resolved if info["changed"] else req.question
sources = rag.retrieve(query)                                   # 用消解后的问句检索
answer  = llm_client.chat_reply(req.question, ctx["history"], sources, ctx["summary"])
memory.remember(session_id, "user", req.question, resolved=resolved)   # 原文入库
memory.remember(session_id, "assistant", answer, sources=sources)
```

### 5.4 两条纪律

1. **原文必须保真。**
   `content` 列存用户原话，`resolved` 另存一列。前端展示、摘要生成、日志排查一律使用原文；`resolved` 只服务于检索。否则对话记录会失真，也无法事后评估消解准确率。

2. **双路召回兜底。**
   消解改写存在猜错风险。当 `rag.retrieve(resolved)` 返回空结果时，回退使用原文再检索一次；或合并两路结果去重。改动量很小，但能显著兜住消解失败的场景。

## 六、会话管理接口

| 接口 | 作用 | 响应 |
|---|---|---|
| `POST /api/sessions` | 新建会话 | `{session_id, created_at}` |
| `GET /api/sessions/{id}/messages` | 拉取历史（APP 重启后回填界面） | `{session_id, messages: [...], summary}` |
| `DELETE /api/sessions/{id}` | 用户主动清除会话 | `{ok: true}` |

对应前端改造（**角色 A**）：

1. `session_id` 存入 `SharedPreferences`，不再每次 `UUID.randomUUID()`；
2. 首次启动或本地无 id 时调用 `POST /api/sessions`；
3. 启动时调用 `GET /api/sessions/{id}/messages` 回填 `ChatUiManager` 的消息列表。

> **降级方案**：若前端本次不便改动，可在后端对空 `session_id` 做兼容（按设备标识生成稳定 id，或复用最近活跃会话）。但这只是补丁——**若不改前端，「会话持久化」在验收演示中无法体现效果**，推荐按标准方案与前端联动。

## 七、落地顺序

| 阶段 | 内容 | 可验证产出 | 预估 |
|---|---|---|---|
| **P0-a** | `store.py` + SQLite；`memory` 内部切到 DB，对外 API 不变 | 重启服务后对话不丢 | 半天 |
| **P0-b** | `coreference.py` 第一级（焦点 + 规则）+ **调整 chat/voice 处理顺序** | 「它是什么年代的」能正确作答 | 半天 |
| **P1-a** | 会话管理三接口 + 前端 `SharedPreferences` 配合 | 重启 APP 后恢复对话 | 一天 |

## 九、风险与注意事项

| 风险 | 影响 | 应对 |
|---|---|---|
| 消解猜错对象 | 答非所问，比不消解更差 | 歧义保护 + 双路召回；`resolved` 与原文分列存储，可回溯评估 |
| LLM 改写增加延迟 | 语音交互体感变慢 | 仅在必要时触发；设超时；失败退回原句 |
| SQLite 并发写锁 | `database is locked` | WAL 模式 + `busy_timeout` + 短事务 + 每请求独立连接 |
| 摘要调用过频 | token 成本与延迟上升 | 仅在跨过阈值时触发一次 |
| 对话全量入库 | 隐私与存储增长 | TTL 清理 + 单会话条数上限；`.gitignore` 排除本地 DB |
| 与角色 C 的 RAG 改造撞车 | 合并冲突、职责重叠 | `retrieve(question)` 签名保持不变；消解放在调用方（`chat.py`）而非 `rag.py` 内部 |

### 分工归属提示

`coreference.py` 逻辑上位于**角色 C 的 `rag.py`** 与**角色 D 的 `memory.py`** 之间。`backend/README.md` 分工表目前将「指代消解」列在角色 D 名下，**开工前需与组内确认**，避免与角色 C 的 RAG 改造重叠。本方案的建议边界是：

- **角色 C**：负责 `rag.py` 内部（查询改写、向量检索、资料切分）；
- **角色 D**：负责 `coreference.py`（对话历史层面的指代消解）与调用顺序编排。
