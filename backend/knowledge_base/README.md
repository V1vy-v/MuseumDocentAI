# 【角色 C 负责】博物馆知识库

把资料文件放进**这个目录**（子目录也可以），服务启动时会**自动切块、向量化并建索引**，
不需要改任何代码、也不用手工跑脚本。

```
knowledge_base/
├── 越王勾践剑.md          ← 文件名 = 资料标题
├── 曾侯乙编钟.md
├── 展厅路线.md
├── 青铜器/                ← 子目录可以，标题仍取文件名
│   └── 铸造工艺.md
└── README.md              ← 本文件，不参与索引
```

## 放什么

- 文物介绍（年代、尺寸、出土地、工艺、流传经历）
- 历史背景资料
- 展厅分布与参观路线
- 书画知识（对应课题"擅长琴棋书画"中的书画方向）

## 规则（都实测过）

| 项 | 说明 |
|---|---|
格式 | **`.md` / `.txt`**。PDF 不行——请先转成 Markdown 再放进来 |
`README.md` | **会被跳过**，它是给人看的说明，不算知识 |
标题 | 取**文件名**（去扩展名）。`示例_` / `demo_` / `sample_` 前缀会自动去掉，所以 `示例_越王勾践剑.md` 的标题是「越王勾践剑」 |
生效时机 | **重启服务**。启动时做增量同步，只重建改动过的文件（约 0.3 秒） |
删除 | 删掉文件后重启，索引里的对应内容也会一并清理 |
强制重建 | 删掉 `backend/data/zvec_kb*` 再启动 |
不要放 | 大图片、扫描件、二进制文件（放了也不会被索引，只是白占仓库体积） |

## 怎么写才检索得准

分块是**按 Markdown 标题切的**，所以结构直接决定检索质量。推荐这样写：

```markdown
# 曾侯乙编钟

## 概况
战国早期大型礼乐重器，1978 年出土于湖北随州擂鼓墩曾侯乙墓，现藏湖北省博物馆。

## 工艺
全套 65 件，总重 2567 公斤，采用分范合铸。每件钟可发两音，音域跨五个半八度。

## 展厅位置
一楼曾侯乙展厅正中。
```

要点：

1. **一级标题写文物名**，二级标题写「概况 / 年代 / 工艺 / 展厅位置」这类主题
2. **一段讲一件事**，别写成一大坨；段落是合并成约 300 字一块的基本单位
3. **事实要具体**——年代、尺寸、出土地、展厅，这些词是检索能命中的锚点
4. 别在正文里写"待补充""TBD"，这些也会被当成资料检索出来

## 现在的状态

链路已经打通，**缺的是内容**。目前只有 1 份示例资料（`示例_越王勾践剑.md`），
所以只有当观众问到越王勾践剑时才有据可依，其他问题都会走"馆内资料暂未收录"。

补充资料的收益很直接：**对演示观感的影响大于任何代码优化**。
按上面的规范补到 10~20 份，检索效果和兜底体验都会有明显提升。

## 技术细节（想了解实现再看）

- 向量化：火山 Ark `doubao-embedding-vision`（2048 维）
- 索引：zvec 进程内向量数据库，HNSW（余弦距离）+ jieba 分词 BM25 全文索引
- 检索：两路融合（RRF），以向量距离为相关性闸门
- 索引目录 `backend/data/zvec_kb/` 已 gitignore —— 分发的是**资料**，索引由各自机器重建
- 详见 `backend/docs/后端README.md` 的 FR-8 与 `backend/docs/接口文档.md`
