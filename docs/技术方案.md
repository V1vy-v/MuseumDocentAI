# 技术方案（调整版）

> 原方案见《基于 RAG 的博物馆导览问答机器人.pdf》。本文档记录**按小组决定做的调整**，与 PDF 冲突时以本文档为准。

## 一、总体目标（不变）

- 平台：安卓原生 APP + Python 后端
- 技能强化：历史博物馆导览（对应课题要求"擅长某个领域"）
- 高阶能力：RAG 检索增强 + 上下文多轮记忆

## 二、关键调整：大模型换成 mimo-v2.5-asr

原方案的大脑是 DeepSeek V4.1（纯文本模型，语音要靠第三方识别转文字）。
现改为 **mimo-v2.5-asr**：它支持**语音直接输入**，省去单独的语音识别环节。

### 新的语音交互链路

```
用户说话
  → APP 录音（角色B）
  → 音频上传到后端（角色A 的网络模块）
  → mimo-v2.5-asr 直接听音频 + 结合 RAG 资料回答（角色C/D 的后端）
  → 回答文本返回 APP 显示（角色A 的界面）
  → 语音播报回答（角色B）
```

### 语音播报（TTS）的两种情况

| 情况 | 做法 |
|---|---|
| mimo-v2.5-asr **支持**语音输出 | 直接用它返回的音频播放 |
| mimo-v2.5-asr **不支持**语音输出 | 后端另外接一个 TTS（文字转语音）API 生成音频；或用手机自带的朗读功能 |

> 该模型的具体接口能力（音频格式、是否流式、是否带语音输出）**待确认**，需要拿到它的 API 文档或控制台说明。确认前，代码里所有模型相关配置都集中在 `backend/app/core/config.py`，换配置不用改逻辑。

### 对分工的影响

- **角色 B（语音）**：不再必须集成讯飞/百度等第三方识别 SDK；重点工作变成"录音质量、上传、播放、打断、延迟优化"。如果后面想做"边说边识别"的实时效果，再考虑本地识别作为补充。
- **角色 D（后端）**：新增"接收音频文件"的接口，并封装 mimo-v2.5-asr 的调用。
- **角色 A（界面）**：基本不变。
- **角色 C（RAG）**：不变。

## 三、对外接口规划（前后端约定）

| 接口 | 方向 | 内容 |
|---|---|---|
| `POST /api/chat` | APP → 后端 | 文本问题 + 会话编号 → 回答 + 资料来源 |
| `POST /api/voice` | APP → 后端 | 录音文件 + 会话编号 → 回答文本 + 资料来源（+ 可选回答音频） |

## 四、待确认问题清单

1. mimo-v2.5-asr 的 API 地址、密钥、调用方式（文档或控制台截图）。
2. 它接受的音频格式（WAV/PCM/MP3？采样率？）和时长限制。
3. 是否支持语音输出（决定 TTS 是否要另接）。
4. 是否支持流式返回（影响"打字机效果"和延迟体验）。
5. 调用限速/并发限制（课程演示时的稳定性）。
