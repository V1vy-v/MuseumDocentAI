# 技术方案（调整版）

> 原方案见《基于 RAG 的博物馆导览问答机器人.pdf》。本文档记录**按小组决定做的调整**，与 PDF 冲突时以本文档为准。

## 一、总体目标（不变）

- 平台：安卓原生 APP + Python 后端
- 技能强化：历史博物馆导览（对应课题要求"擅长某个领域"）
- 高阶能力：RAG 检索增强 + 上下文多轮记忆

## 二、关键调整：大模型换成 mimo-v2.5-asr

原方案的大脑是 DeepSeek V4.1（纯文本模型，语音要靠第三方识别转文字）。
现改为 **mimo-v2.5-asr**：它支持**语音直接输入**，省去单独的语音识别环节。
（已实测：同一平台还有 **mimo-v2.5-tts** 负责语音输出，因此**不需要**另接第三方 TTS API。）

### 新的语音交互链路

```
用户说话
  → APP 录音（角色B）
  → 音频上传到后端（角色A 的网络模块）
  → mimo-v2.5-asr 听懂提问（角色D 的后端）
  → 结合 RAG 资料 + 对话历史生成回答（角色C/D 的后端）
  → mimo-v2.5-tts 把回答变成语音
  → 回答文本 + 语音返回 APP（角色A 显示、角色B 播报）
```

### 模型调用方式（已实测确认，接口为 OpenAI 兼容格式）

| 能力 | 模型 | 调用 |
|---|---|---|
| 听懂语音 | mimo-v2.5-asr | `POST {API}/chat/completions`，用户消息带 `input_audio`（base64 WAV） |
| 文本回答 | mimo-v2.6-flash | 同上，标准 messages（带 system 人设 + 对话历史 + 检索资料） |
| 语音播报 | mimo-v2.5-tts | 同上，messages 里放 assistant 角色的文本，回复的 `message.audio.data` 是 base64 音频 |

> API 地址与密钥配置在 `backend/app/core/config.py` + 本地 `backend/.env`（不入库）。
> 后端已实测跑通"语音提问 → 回答 → 语音播报"完整闭环（`backend/scripts/smoke_test.py` 可复验）。

### 对分工的影响

- **角色 B（语音）**：不再必须集成讯飞/百度等第三方识别 SDK；重点工作变成"录音质量、上传、播放、打断、延迟优化"。
- **角色 D（后端）**：新增"接收音频文件"的接口，并封装 mimo-v2.5-asr 的调用。（已实现）
- **角色 A（界面）**：基本不变。
- **角色 C（RAG）**：不变（当前是关键词匹配占位实现，向量检索待补）。

## 三、对外接口规划（前后端约定，已实现）

| 接口 | 方向 | 内容 |
|---|---|---|
| `POST /api/chat` | APP → 后端 | 文本问题 + 会话编号 → 回答 + 资料来源 |
| `POST /api/voice` | APP → 后端 | 录音文件(WAV) + 会话编号 → 识别的提问 + 回答文本 + 资料来源 + 回答音频(base64) |
| `GET /api/health` | APP → 后端 | 健康检查，联调用 |
